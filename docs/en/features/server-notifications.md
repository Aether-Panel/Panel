# Server notifications

Each server can send its own alerts to the places its owner already uses: a Discord channel, a Telegram chat, or any system that accepts a JSON webhook. These alerts are configured per server, by whoever manages it, and are independent of the panel-wide administrator alerts described in [Discord webhooks](../general/16-discord.md) and [Email](../general/15-email.md).

## What it does

- Sends an alert when the server **crashes**, when a **backup** finishes or fails, when **CPU or memory stay high**, and (optionally) every time the server **starts or stops**.
- Delivers each alert to every channel configured: Discord, Telegram and a generic webhook can be used at the same time.
- Includes the last console lines in crash alerts.
- Offers a **test** button that posts a sample message to every channel and reports which ones failed.

A new server has no channel configured. The events **Crashes**, **Backups** and **High resource use** are on by default, so they start working as soon as a channel is added; **Start and stop** is off.

## How it works

### Where the settings live

The settings are stored on the node that runs the server, in `<daemon.data.servers>/<serverId>.notify` (file mode `0600`). They are kept out of the server definition on purpose: webhook URLs and bot tokens are secrets, and the definition can be read by more users. The file is deleted together with the server.

Because the node keeps the settings and sends the alerts, **the node needs outbound internet access** to Discord, Telegram or the webhook host.

### When each event fires

| Event | Trigger | Content |
|-------|---------|---------|
| Crash (`crash`) | The process exited with a code different from the template's expected exit code, and nobody asked for a stop or kill. | Exit code, whether the server is restarting by itself (attempt *n* of `daemon.data.crashLimit`), and the last 12 console lines. |
| Backup (`backup`) | A backup finishes, successfully or not. | Success or failure. |
| High resource use (`resources`) | Checked every 5 seconds while the server runs: CPU above **80 %** of what the server may use, or memory above **90 %**. | Resource, current value and threshold. At most one alert every **5 minutes** per resource while it stays high; the counter resets once usage drops below the threshold. |
| Start and stop (`power`) | The server's running state changed between two 5-second samples. | Online or stopped. This also fires for stops someone requested. |

The first sample after the daemon starts only records the current state, so restarting the daemon does not send alerts. A very short start/stop that happens between two samples can go unnoticed by the power event.

Alerts are sent in the background: a slow or unreachable channel never delays the server. Delivery errors are written to the server's log (`Error sending <channel> notification: ...`).

### Channels

| Channel | What is sent |
|---------|--------------|
| Discord | One embed with a title, a description (server name in bold, console lines in a code block, trimmed to the last 3,500 characters), a colour per event and the footer `Aether Panel · <serverId>`. |
| Telegram | One HTML-formatted message through the bot (`sendMessage`, link previews off). Console lines are trimmed to the last 3,000 characters. |
| Webhook | A JSON `POST` (see below), with `User-Agent: AetherPanel-Webhook/1`. |

The alert titles and messages are generated by the node in the **notification language**, `panel.settings.notificationLanguage` (`es` by default, or `en`), not in the language of the person reading the panel. On the panel's own node it is set in **Settings › General › Notifications** (see [Panel settings](panel-settings.md)); a remote node reads its own configuration, so its servers' alerts follow the value set on that node (the panel does not push it). The example below is in Spanish; in English the title is `💥 Server crashed`.

### Webhook payload

```json
{
  "event": "crash",
  "title": "💥 Caída del servidor",
  "message": "Survival se ha caído (código de salida 137). Se está reiniciando solo (intento 1 de 3).",
  "server": { "id": "a1b2c3d4", "name": "Survival" },
  "timestamp": "2026-11-01T10:15:00Z",
  "lines": ["...last console lines..."],
  "exitCode": 137,
  "restarted": true
}
```

`event` is `crash`, `backup`, `resources`, `power` or `test`. `lines` only appears when there are console lines. Extra fields per event:

| Event | Extra fields |
|-------|--------------|
| `crash` | `exitCode`, `restarted` |
| `backup` | `success` |
| `resources` | `resource` (`CPU` or `Memoria`, whatever the notification language, so receivers keep working), `value`, `threshold` |
| `power` | `running` |

**Signature.** When a signing secret is set, every request carries `X-Aether-Signature: sha256=<hex>`, the HMAC-SHA256 of the raw request body keyed with the secret. Compute the same HMAC on the receiving side and compare it before trusting the request.

### Extensions

On a node that also runs the panel, the same events are handed to installed extensions (`server.crashed`, `server.backup`, `server.resources`, `server.started`, `server.stopped`) whatever the owner's notification settings are. See [Extensions](../reference/15-extensions.md).

## Using it

### In the panel

1. Open the server and go to its **Settings** tab. The **Notifications** card is at the bottom of the page. It is only shown to users with the `server.flags.edit` permission on that server.
2. Pick a channel tab (**Discord**, **Telegram** or **Webhook**) and fill in its fields. A green dot on a tab means that channel is configured.
   - **Discord webhook**: in Discord, channel settings → Integrations → Webhooks → New webhook → Copy URL.
   - **Telegram**: **Bot token** (create a bot with `/newbot` in @BotFather) and **Chat or channel ID** (a number, groups start with `-100`, or `@your_channel`). Add the bot to the group or channel first.
   - **Webhook**: **Webhook URL** (`https://` only) and an optional **Signing secret**.
3. Under **What to send**, switch on the events you want: **Crashes**, **Backups**, **High resource use**, **Start and stop**. The **Preview** shows what the messages look like.
4. Click **Save**, then **Send test**. Save first: the test uses the saved settings, not the values on screen.

To turn a channel off, empty its fields and save.

### Via the API

| Method | Path | Scope | Purpose |
|--------|------|-------|---------|
| `GET` | `/api/servers/:serverId/notifications` | `server.flags.edit` | Read the settings (channels and event switches). |
| `PUT` | `/api/servers/:serverId/notifications` | `server.flags.edit` | Validate and save the settings. Answers `204`. |
| `POST` | `/api/servers/:serverId/notifications/test` | `server.flags.edit` | Send a test to every channel. Answers `200` with one result per channel, `"ok"` or the reason it failed. |

The body of `PUT` (and the answer of `GET`) is:

```json
{
  "discordWebhook": "https://discord.com/api/webhooks/123/abc",
  "telegramBotToken": "",
  "telegramChatId": "",
  "webhookUrl": "",
  "webhookSecret": "",
  "crash": true,
  "backup": true,
  "resources": true,
  "power": false
}
```

Saving is recorded in the server's activity log as `settings.notifications`; tests are not recorded. Full details are in the [API reference](../reference/11-api-reference.md).

## Requirements and configuration

Everything is configured per server, except the language of the texts. Related keys:

| Key | Default | Environment variable | Effect |
|-----|---------|----------------------|--------|
| `daemon.data.servers` | `servers` (inside the data folder) | `SKYPANEL_DAEMON_DATA_SERVERS` | Folder where the `.notify` file is stored. |
| `daemon.data.crashLimit` | `3` | `SKYPANEL_DAEMON_DATA_CRASHLIMIT` | Automatic restarts after a crash; shown in the crash alert as "attempt *n* of *limit*". |
| `panel.settings.notificationLanguage` | `es` | `SKYPANEL_PANEL_SETTINGS_NOTIFICATIONLANGUAGE` | Language of the alert titles and messages (`es` or `en`), read by the node that sends them. |

See [Configuration](../backend/02-configuration.md) for how keys and environment variables are read.

## Limits

- **Validation** (applied when saving, and again before sending):
  - Discord: must match `https://discord.com/api/webhooks/<id>/<token>` (also `discordapp.com`, `ptb.` and `canary.`).
  - Telegram: the token must look like `123456789:AA…` (digits, a colon, at least 30 characters) and the chat ID must be a number of up to 20 digits (optionally negative) or `@name` (5–32 characters). Both are required together.
  - Webhook: an `https://` URL with a host and no user/password part.
- **Private addresses are refused.** Every request uses an HTTP client that refuses to connect to loopback or private IP addresses, so a webhook cannot be used to reach the node's own network. A webhook on a LAN host will therefore fail.
- Telegram and webhook requests time out after 10 seconds. Only `2xx` answers count as delivered. There is no retry: a failed alert is logged and dropped.
- The test button can be used once every **10 seconds** per server.
- The thresholds (80 % CPU, 90 % memory, 5 minutes between alerts) are fixed in the code.

## Troubleshooting

| Message | Cause and fix |
|---------|---------------|
| `the URL is not a Discord webhook (https://discord.com/api/webhooks/...)` (400) | The Discord field holds something other than a webhook URL. Copy the URL again from the channel's Webhooks page. |
| `the Telegram bot token or chat id is not valid` (400) | Wrong token format, missing chat ID, or a chat ID with spaces or letters. Use the token from @BotFather and a numeric ID or `@channel`. |
| `the webhook must be an https:// URL` (400) | Plain `http://`, a missing host, or `user:pass@` in the URL. Use HTTPS; put authentication in the signing secret instead. |
| `add a Discord webhook, a Telegram bot or a webhook URL first` (400, test) | No channel saved yet. Fill one in and click **Save** before testing. |
| `wait a few seconds before sending another test` (429) | Two tests within 10 seconds. Wait and try again. |
| `discord webhook returned status 404` | The webhook was deleted in Discord. Create a new one and save it. |
| `telegram answered with status 400` / `403` | The bot is not in the chat, was blocked, or the chat ID is wrong. Add the bot to the group/channel (as admin for channels) and check the ID. |
| `telegram: could not reach the server` / `webhook: could not reach the server` | The node cannot reach the host: no outbound internet, DNS failure, timeout, or the webhook resolves to a private address. |
| `webhook answered with status <n>` | The receiver rejected the request. Check its logs; if it validates the signature, make sure it uses the same secret and the raw body. |
| No alerts arrive although the test works | The event is switched off, or the condition was not met (for example, a stop requested from the panel is not a crash; CPU must exceed 80 % of the server's own limit). |
